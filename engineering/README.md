## 今後の記録方法

開発・設定変更・実サービス確認を行ったら、関連する文書も同じ変更で更新する。

- 判断は「何を選んだか」に加えて、要件、理由、制約、見送った案を残す。
- 不具合は症状、原因を確定した観測、修正、回帰確認、コミットを残す。推測しかない場合は、その旨を書く。
- 検証は実行日、対象コード・環境、操作またはコマンド、期待値と結果を残す。
- 実装済み、設定済み、実サービス確認済み、未整備を混同しない。
- 実測値には単位と測定範囲を付ける。単発の観測を平均値・改善率・一般的な保証へ広げない。
- 長い生ログを貼る代わりに、原因を示す最小限の抜粋と、コード・テスト・CIへのリンクを残す。

日ごとの知見は `lessons-YYYY-MM-DD.md`、まとまった実確認は `verification-YYYY-MM-DD.md` を追加し、この一覧へリンクする。構成・運用の文書は現状を更新し、過去の検証記録は当時の条件を保持する。

## 保存する情報の範囲

Secretの値、OAuthのcode・access token・refresh token、認証ヘッダー、個人のカレンダーID・予定・閲覧履歴は記録しない。サービス名、役割、公開URL、Secretの名前、設定方法は記録できる。

実画面の証拠は、架空課題とDOPAGAKIのUIだけが写るものを選んだ。素材の出典は [ASSETS.md](../ASSETS.md) を参照。スクリーンショットを発表に転載する場合も、提供素材の利用条件の確認は別に必要。

ローカルの `.local/` はGit管理外であり、共有できる運用手順や証拠の唯一の保管場所にはしない。このディレクトリには秘密情報もあるため、まとめて共有しない。
