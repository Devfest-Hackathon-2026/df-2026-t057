# セキュリティ確認とHTTP・拡張の整理

2026-11-07、日本時間。`35544e2` から `codex/security-refactor` ブランチを作り、専用worktreeで確認した。対象はAPI、管理画面、Chrome拡張、依存定義、配信設定のコード。クラウド設定の変更や本番への配信は行っていない。

## 修正した箇所

| 対象 | 確認した問題 | 修正と根拠 |
|---|---|---|
| JSON入力 | 最初の値だけをデコードしていたため、別のJSON・不正文字列・64 KiBを超える後続空白を付けた課題登録が200になった。`null`も構造体へデコードでき、プロフィール更新の意図が不明確だった | 本文全体を64 KiBに制限し、未知のフィールドを含まない単一オブジェクトだけ受け付ける。拒否時に保存内容が変わらないことも確認 |
| 認証 | デモでは32桁のトークンを認証方式なしで送っても本人データへ接続できた。Cookieも長さだけを確認していた | デモは`Demo`、本番は`Bearer`の認証方式を必須にし、デモCookieも発行時の32桁小文字16進数へ制限。本番の署名検証を迂回できたという発見ではない |
| エラー応答 | Geminiの課題抽出・予定調整がSDKのエラー詳細を返し、Firestore・Calendar・OAuthなども外部サービスの詳細を返す経路があった | Geminiの2経路を既存の`sourceError`へ統一。HTTP共通処理でgRPC・Google API・OAuthトークン取得・URL通信エラーを一般化し500を返す。検証エラー・予定競合・課題未検出の案内は保持。fixtureの内部情報が応答へ出ないことを確認 |
| Calendarの公開受付 | state・codeやchannel ID・tokenが欠けてもFirestore参照へ進んでいた | 発行するstate/channel/tokenの形式とcodeの存在をDB参照前に検証。無効なcallbackは既存のエラー画面へ戻し、無効なWebhookは403。形式が正しい未知IDについては既存のDB照合が必要 |
| 拡張のデータ範囲 | APIのState全体を保存・content scriptへ配信しており、プロフィール、報酬履歴、記憶の再送記録、課題メモ、Calendar内部IDまで含まれていた | タイマー・通知・スヌーズに使う型とデータを明示し、不要な項目を除外。`storage.local`を`TRUSTED_CONTEXTS`に制限。Node fixtureとChromium E2Eで確認 |
| Go依存 | `govulncheck`が`golang.org/x/crypto v0.58.0`のモジュール内にGO-2026-5932を報告した。該当OpenPGPパッケージのimport・呼び出しは検出されなかった | 公式DBに記載された境界の`v0.58.1-0.20261009181718-2f1f834330b2`へ最小更新し、再監査で検出0件。照会時点でタグ版の一覧はv0.58.0までだった |

拡張の変更は、任意のWebページのJavaScriptが従来の全データを直接読めたという実証ではない。content scriptとWebページは別の実行環境であり、今回は拡張側で保持・配信する情報とAPIアクセス権限を減らした。[ChromeのStorage APIの仕様](https://developer.chrome.com/docs/extensions/reference/api/storage)を参照。

Goの報告は非保守のOpenPGP実装に関するもの。[GO-2026-5932](https://pkg.go.dev/vuln/GO-2026-5932)を参照。更新前からこのAPIの該当パッケージへの到達は検出されていないため、本サービスで悪用可能だったと扱わない。

## リファクタリング

- 認証・本人識別を`api/internal/app/auth.go`、JSON・HTTP応答を`api/internal/app/http.go`へ分離した。
- 複数の受付で毎回作成していた同じID用正規表現を共有した。
- 拡張専用の`ExtensionState`・`ExtensionTask`を定義し、API応答から拡張へ渡す項目を1箇所で選ぶようにした。
- 既存の4200番サーバーを使わず確認するため、Playwrightに`E2E_PORT`を追加した。拡張の接続先も同じポートへビルドする。

## 検証

Node.js 24.22.1、Go 1.27.3、ローカルのデモとHTTP fixtureを使用。有料APIの実接続は行っていない。

| 検証 | 結果 |
|---|---|
| 修正前の再現 | 複数JSON・不正な末尾・サイズ上限を超える後続空白の登録が200。認証方式を欠くデモトークンも200。追加した回帰テストの失敗を確認 |
| `npm run build` | 管理画面・拡張の生成成功 |
| `npm test` | 拡張型チェック、Node 4件、Go race成功。本人分離・報酬・時刻・競合の既存テストも含む |
| `go vet ./...` | 成功 |
| `npm run test:e2e` | 専用ポート4276で12件成功。拡張の通知・計測・作業・スヌーズと保存領域のアクセス拒否を含む |
| `npm audit --json` | ロックファイルに対する既知の脆弱性0件 |
| `govulncheck ./...` | 更新後は既知の脆弱性0件 |
| 秘密情報の限定パターン照合 | Git追跡ファイル175件で秘密鍵、GitHub・Slackトークン、AWSアクセスキー形式の一致0件。Git履歴・画像・全形式の資格情報を網羅する検査ではない |

独立したworktreeでE2Eを実行する場合の例：

```bash
npm run build
APP_URL=http://127.0.0.1:4276 npm run build:extension
CI=1 E2E_PORT=4276 npm run test:e2e
```

拡張の生成物は接続先ごとに固定される。公開先へ導入する際は、その公開オリジンで改めてビルドする。

## 確認できた境界と残る課題

コードでは、本人データの保存先を署名検証後のUIDから決め、本文で指定させていない。Calendar OAuthは期限付きstateをトランザクション内で一度だけ消費し、Google subjectを照合する。Firestoreのクライアント用ルールは全面拒否。拡張の接続情報は`storage.session`を使い、管理画面のオリジンを確認する。既存の本人分離・再送テストも成功した。

この結果は全体の安全性の保証ではない。次の項目は今回の完了範囲と分ける。

- **次に優先する実装：有料AI呼び出しの利用上限。** 相談には同時処理用のleaseがあるが、課題抽出・登録時の手順作成・予定調整を含む利用者単位の回数・日次上限はない。認証済み利用者による連続利用への制御が必要。Cloud Runのインスタンス上限だけを費用上限と扱わず、複数インスタンスで共有する制限と利用条件を設計する。
- **本番設定は未確認。** IAMの最小権限、Secret Managerの権限、実際に適用されたFirestoreルール、OAuth公開設定、実利用者間の分離を今回のローカル試験から断定しない。
- **ブラウザー側の追加防御。** 配信コードには`X-Frame-Options`・`nosniff`等があるがCSPは未設定。Firebase認証・Angular・Calendar表示の必要な通信・style等を計測して設計する必要がある。
- **監査の限界。** SDKのエラー詳細はサーバーログに残るため、運用ログの閲覧権限と保存期間も確認対象。OS・コンテナー全体、Git履歴、侵入試験、実OAuthフローは今回検査していない。
