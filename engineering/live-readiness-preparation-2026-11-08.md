## ① 拡張が認証状態を維持する

### 採用案と操作

拡張のService Workerで`firebase/auth/web-extension`を利用し、Firebase SDKの永続化・IDトークン更新を使う。ユーザー操作でポップアップからGoogleログインし、以降のAPI呼び出しは拡張のFirebaseユーザーから取得したIDトークンを送る。長期Bearerの独自発行や、Webからrefresh tokenをコピーする仕組みは作らない。

Googleログインは公式のOffscreen Documents方式を第一候補とする。専用の認証ページをOffscreenのiframeへ読み込み、認証結果から拡張側の`signInWithCredential`でセッションを確立する。認証結果を受け取るだけでService Worker側にもログイン済みになったと扱わない。

| 状態 | ポップアップ・動作 |
|---|---|
| 未接続 | 「Googleで接続」。操作時だけ認証画面を開く |
| 復元中 | 「接続を確認中」。復元完了前にAPIを送らない |
| 接続済み | 本人のメール、最終同期時刻、管理画面へのリンク |
| 一時的な通信失敗 | 「通信待ち」。認証は保持し、既存の予定を消さない |
| 再認証が必要 | 通知バッジと再ログインボタン。バックグラウンドで認証画面を開かない |
| Webと拡張のアカウントが異なる | 両方のアカウントを明示し、拡張で切替操作を求める。自動切替しない |

### 接続・実装箇所

- `background.ts`：SDKの初期化・認証復元後にAPIを呼ぶ。期限切れと通信失敗を区別し、401での強制更新は一度まで。変異リクエストの再送は既存の冪等性が保証される操作だけにする。
- `protocol.ts`・`content.ts`・`api.ts`：本番のWeb→拡張Bearer転送を廃止する。管理画面からは接続診断と、認証済みの拡張ユーザーと一致するログアウト要求だけを扱う。デモ接続は別経路で維持する。
- `popup.ts`・ポップアップHTML：本人の確認、接続・切替・解除、状態表示。
- 新設する拡張の認証モジュール・Offscreen用HTML/TS・認証専用Webページ。ファイル名は実装時に既存構成へ合わせる。
- `scripts/build-extension.mjs`：上記をバンドルし、Offscreen権限と必要な接続先を追加。拡張IDと公開オリジンをビルド単位で固定する。
- `main.go`：埋め込みを許可するのは認証専用ページだけ。既存画面の`DENY`は維持し、専用ページのCSP `frame-ancestors`は許可した拡張IDに限定する。`postMessage`はorigin・source・処理IDを照合する。

アカウント切替・ログアウトでは、SDKのログアウト、状態キャッシュ、通知、通知済み計画、計測中の未送信分をまとめて解除する。`connectionVersion`相当の版管理を残し、全ての遅延応答の採用前に確認する。

アラーム起動時には認証復元→状態取得→予約再構築を行う。初回の変更ではオフライン中の通知保証までは広げず、通信待ちの状態と再試行を明示する。

### 着手後に最初に検証する点

Firebase SDKの認証復元がService Workerの停止・再起動をまたいで機能すること、専用ページの埋め込みとGoogleログインが現在のCSP・Firebase設定で成立することを、最小の認証経路で先に確認する。成立前に全画面・全APIへ変更を広げない。この検証自体も今回は実行しない。

公開拡張ID、Firebaseの許可設定、Googleログイン時の必要な接続先は現クラウド設定の確認待ち。現在の設定で動くと断定しない。

## ③ Google同期の状態と競合を解消する

### 状態とAPI案

課題の同期状態を`in_sync / pending / retrying / reauth_required / conflict`とする。既存の`calendarSync`は移行中の集約表示として残し、画面の詳細は課題別の状態を使う。

| API案 | 入出力と意味 |
|---|---|
| `POST /api/calendar/sync`（既存） | 利用者自身の同期。通信失敗と再認証・競合を機械判定できるエラーコードを返す |
| `GET /api/calendar/conflicts` | 本人の競合一覧。課題ID、アプリの入力、Googleの入力、現在のETag・版 |
| `POST /api/tasks/{id}/calendar-resolution/preview` | 採用先または編集した入力から、既存の予定検証を使って変更前後を返す |
| `POST /api/tasks/{id}/calendar-resolution/commit` | `requestId`、プレビューの版、ETag、本人の選択で確定。再競合は409 |

競合画面は「アプリを使う／Googleを使う／編集する」の3択とする。Googleにない`why`と作業リンクは保持し、空値で消さない。Google側の削除は、再作成かアプリ側の課題削除を明示して選ぶ。進行中・完了済みの課題の内容編集を、この画面から迂回して許可しない。

Googleイベントの開始・終了は現在の「締切−必要時間／締切」、実際の作業計画は説明欄のDOPAGAKIブロックという対応を維持する。既存の計画検証を再利用し、②の時間割機能は足さない。

### 再試行・保存

- 現在の入力ハッシュに加え、最後に同期できた入力を保存する。本人の確定内容とGoogleの新しい内容を失わない。
- `lastAttemptAt / retryAt / attempts / errorCode`を利用者・課題単位で保持。認証失効・競合は自動上書きの対象にしない。
- 一時失敗は初期案として1分・5分・30分・以降1時間の間隔で再試行。手動同期はすぐ実行でき、同じ対象の並行実行はリースで抑止する。
- 再試行はCloud Runのレスポンス後の常駐処理に頼らず、Schedulerから期限到来分を小さなバッチで処理する。Schedulerが実際に再試行したかを成功表示の条件にしない。
- Googleへの保存成功・応答喪失でも同一`requestId`とハッシュで再実行できるようにする。Firestore側は確定入力を先に保留し、Google成功後に反映済みにする。
- 自分自身の再書き込みによるWebhookで、再抽出・報酬・履歴を増やさない。

`renewCalendar`は1人の失敗後も次の利用者へ進み、全体の成功・失敗件数を返す。権限失効した利用者は再連携待ちに分け、他の利用者の更新を繰り返さない。監視作成時には`resourceId`も保存し、⑥の停止処理に使う。

変更箇所：`calendar.go`、`server.go`、`model.go`、`shared/models.ts`、`app.html`、設定・カレンダー画面、競合用Material Dialog。初期の同期状態は既存保存形式へ追加し、⑤の保存分離時に課題文書へ移す。

## ⑤ アーカイブと記録・報酬の独立保存

### 保存先の案

ユーザー配下にまとめ、既存の認証・直接アクセス拒否を維持する。API経由で必要な範囲だけ取得する。

| 保存先案 | 主な内容・キー |
|---|---|
| `users/{uid}` | `schemaVersion`、残高、プロフィール、設定、予定の版、進行中セッション、状態の版 |
| `users/{uid}/tasks/{taskId}` | 課題本体、`archivedAt`、同期状態。アーカイブは完了課題だけに許可 |
| `users/{uid}/completions/{taskId}` | 課題名の記録用コピー、完了日時、実際の報酬、得られている場合だけ実績時間 |
| `users/{uid}/ledger/{entryId}` | 初期付与・登録・完了の確定記録。既存の種別＋課題IDを安定したIDとして使用 |
| `users/{uid}/operations/{requestId}` | 再送の結果、操作種別、対象ID。⑦の操作にも利用 |
| `users/{uid}/activityEvents/{eventId}` | ⑦の行動記録。動画URLや閲覧履歴を含めない |

報酬を伴う操作は、課題・完了記録・台帳・残高をFirestoreトランザクションで確定する。台帳を表示用の直近範囲へ絞っても、加算済みの判定は永続するIDで行う。現在の`grant`の「取得済み台帳を全走査」をそのまま残さない。課題を消した後にCalendarから同じIDが再取り込みされても再付与しない。

APIのStateと保存形式は分ける。通常の`/api/state`は未完了の課題、現在のタイマー、残高、設定、必要な直近表示だけを返す。200件の制限は未完了課題に対して適用し、完了課題は別APIでページ取得する。

互換性は`/api/config`の`apiVersion / minClientProtocol`と、Web・拡張が送る`X-Dopagaki-Client-Version`で判定する。保存分離前は旧契約を維持し、切替後の利用者に未対応クライアントからアクセスが来たら、データを返す前に更新が必要なエラーを返す。版の自己申告は互換性確認だけに使い、所有者確認には使わない。全件の台帳を前提とする旧クライアントへ、黙って一部だけ返さない。

| API案 | 用途 |
|---|---|
| `GET /api/tasks?status=completed&archived=…&cursor=…` | 完了・アーカイブ一覧。上限付きページ取得 |
| `PUT /api/tasks/{id}/archive` | `{archived: true/false, requestId}`。復元でも報酬を付与しない |
| `GET /api/records?from=…&to=…&cursor=…` | 期間別の完了記録と報酬。検索範囲の上限を設ける |

アーカイブはGoogleイベントを変更しない。従来の「削除」と区別し、課題削除後も独立した完了記録は残す。記録そのものの消去は⑥の削除操作で扱う。Calendar取消の取り込みでも、完了記録・付与済みIDは消さない。

### 既存データの移行手順案

1. 先に新しい保存形式を読み書きできるサーバーと、記録・完了一覧APIを使うWeb/拡張を準備する。機能・プロトコル版を検査し、古いWebは更新を案内、古い拡張は更新が必要と表示する。部分的なStateを旧画面へ黙って返さない。
2. 移行ツールは読み取り専用のdry-runを既定にする。件数・IDの重複・元残高・報酬ID・完了記録の候補を出力し、本文や秘密情報はログへ出さない。今回はツール自体を作らない。
3. 利用者ごとに更新を一時停止し、進行中の処理を完了または失効させる。Web・拡張・Webhook・AI保存の全入口で停止を確認し、保存済みセッションは保持する。
4. 復元用の旧スナップショットをアクセス制限した保存先へ取得する。復元確認前に本番を移行しない。保存期限を決め、退会削除時の対象にも含める。
5. 決定的な文書IDで課題・台帳・完了記録をコピーする。複数バッチになっても再実行で重複しない。移行先が揃うまで旧形式を正とし、`schemaVersion`は最後に切り替える。
6. 元の残高、課題と台帳のID集合、完了件数、進行中タイマー、Calendar対応、同期保留、記憶文脈の境界を照合する。移行は通常の登録・完了APIを呼ばず、報酬を計算し直さない。
7. 切替後に更新を再開し、アーカイブとページ取得を少人数で確認する。復元用コピーは保管期限後に削除する。

重要な移行例外：現在は視聴消費を台帳に保存していないため、**台帳の合計を残高として再計算しない**。元の残高をそのまま引き継ぐ。削除済み課題の完了が台帳にだけ残る場合、完了記録は元の完了報酬の日時・額で復元し、課題名は「削除済みの課題」、実績時間は不明とする。存在する課題の`completedAt`と台帳の日時が食い違う場合はdry-runで差分として報告する。

切替前の失敗は旧形式のまま再開する。切替後に新規書き込みがあった場合、古いスナップショットへ単純に戻すと最新の残高等を失う。対応済みサーバーでの修復を優先し、戻す場合は更新停止・現行データからの逆変換・照合が必要。アプリのリビジョン切替だけではデータ移行を取り消せない。

変更箇所：`store.go`のStore境界、`model.go`の付与処理、各変異API、Calendar取り込み・削除、assistantの課題取得、`shared/models.ts`、課題・記録画面、`activity.ts`。永続層以外の計画計算はそのまま使えるようにする。

## ⑥ 連携解除・会話削除・書き出し・退会

### 操作を分ける

| API案 | 操作・扱い |
|---|---|
| `POST /api/calendar/disconnect` | アプリ内のCalendar連携を停止。課題・残高・記録は残す |
| `POST /api/assistant/delete-history` | `{requestId, deleteMemory}`。保存会話を削除し、作業傾向の削除は別選択 |
| `GET /api/account/export?format=json` | 版と取得時点付きの本人データ。秘密情報・OAuth状態・トークンは含めない |
| `GET /api/account/export?format=csv&kind=tasks/completions` | 一覧をCSVで取得。表計算ソフトの数式として実行される値を無害化する |
| `POST /api/account/deletion` | 最近の再認証、`requestId`、専用カレンダー削除の選択を検証して受付 |
| `GET /api/account/deletion` | 本人の削除進行・失敗・完了を取得。通常データにはアクセスさせない |

書き出しはAPIの期間・件数制限を内部でページ処理し、取りこぼしを防ぐ。取得開始時の版を記載し、途中でデータが変わった場合は再取得を求めるか、固定したスナップショットから出力する。Secret、他ユーザーの情報、認証ヘッダーを出力しない。

### Calendar連携解除の前提補正

前の会話では通常の連携解除にOAuth許可の取り消しまで含めたが、Google公式資料ではtoken revokeは同じプロジェクトの他クライアントの認可にも影響するとされる。①のGoogleログインとの影響もあるため、**通常のCalendar連携解除と、Google側のアクセス許可全体の取り消しを同じ操作にしない**。

通常解除は、接続状態を停止→監視チャンネルの停止→保存トークンの削除とする。Google側の許可が取り消されたとは表示しない。必要な人にはGoogleアカウントの接続管理から取り消す導線を出す。退会時にプログラムからrevokeする場合は、対象プロジェクト内での影響を表示し、専用カレンダー削除等の必要なAPI処理を先に完了する。

通常解除では再連携用に既存の専用Calendarの対応だけを残す。再連携時に本人の同じCalendarを確認して再使用し、同名のCalendarを増やさない。Google側でCalendarが消えている場合だけ新規作成し、残した課題の再登録を本人に確認する。退会ではこの対応情報も削除する。

監視の停止にはチャンネルIDと`resourceId`を使う。旧チャンネルで`resourceId`がない場合は、認証済みWebhookのヘッダーと対応確認して補完するか、有効期限までの残存監視を記録する。どちらの場合もアプリ側では停止した接続のWebhookを無視し、データを再作成しない。

トークン削除はSecretの最新バージョンだけを消して終わりにせず、ユーザー専用Secret全体を対象にする。共有のOAuth client secretとScheduler secretは削除対象外。必要なSecret削除権限は現在の権限にあると仮定せず、ユーザー専用Secretに限った最小権限を確認する。

### 再実行できる削除

`accountOperations/{uid}`に種別・処理ID・段階・再試行時刻を保持する。アカウント削除は`closing → external_cleanup → data_cleanup → auth_cleanup → completed`として進める。保守処理は認証されたSchedulerから少量ずつ再開し、Cloud Runのレスポンス後のバックグラウンド実行に依存しない。

受付時にアカウントの世代を更新し、全API、Firestore更新、AIの`Finish`、Calendar callback/Webhook、同期・監視更新で状態と世代を確認する。認証用middlewareだけでは、受付前に開始した処理を止められないため、保存トランザクションでも確認する。外部Calendar書き込みが処理中だった場合はその結果の突合・後始末まで終えてから削除完了にする。

削除対象は、ユーザー状態、課題、完了記録、台帳、再送記録、行動記録、会話の全turn、会話のリース、OAuth state、Calendar接続・チャンネル、ユーザー専用Secret、書き出し用一時データ、移行時の復元用コピー、Firebaseユーザー。Firestoreは親文書削除だけでは子コレクションが消えないため、子までバッチ処理する。

Firebaseユーザーは最後に削除する。受付時には推測困難な状態確認用トークンを一度だけ返し、サーバーはハッシュだけ保持する。上記の削除状態APIは、Firebaseユーザー削除後にはこのトークンでも進行段階だけを取得できるようにし、他の本人情報やデータ取得には使わせない。URL・ログにトークンを含めず、処理記録の保持期限で失効させる。

既発行トークンの署名検証だけで削除後に初期Stateが再作成されないよう、失効・ユーザー削除の検出と、処理中リクエストの保存禁止を組み合わせる。削除処理の記録は本文を持たない最小限とし、遅延処理を遮断する期間を過ぎてから消す。保存期間は実装前に運用として決める。

会話削除も世代を更新し、削除前に開始した相談の応答が履歴へ戻らないようにする。新しい相談は処理完了後から受け付ける。作業傾向を残す選択なら保持するが、削除済み会話を新規相談の文脈に戻さない。

プライバシーページは、実装・確認が終わった操作だけに更新する。Google側の専用カレンダーは既定で残し、削除は本人の明示選択とする。未確認のクラウドバックアップ・ログについて「全保存先から即時消去」とは案内せず、実際の保持設定を別途確認する。

変更箇所：認証middleware、Store全更新、assistant保存、Calendar各入口、新設account処理、設定画面、公開のデータ取り扱いページ。必要なIAM・Scheduler・Firebase設定は実装後の確認項目とし、今回は変更しない。

## ⑦ 振り返りの記録と週次表示

②の中断・切替機能は追加しない。既存の開始・一時停止・再開・完了と、確定したスヌーズだけを記録する。

| 記録 | 保存する事実 | 数えないもの |
|---|---|---|
| 開始 | サーバー日時、開始時点の予定開始、課題ID、予定の版 | 同じ開始の再送、タイマーの再表示 |
| スヌーズ | 確定日時、変更前後、対象課題、`requestId` | 候補表示、キャンセル、通常の手動調整 |
| 一時停止・再開 | セッションID、操作日時、明示的な停止状態 | 同じ状態への再送 |
| 完了 | 完了日時、開始があればタイマー上の作業秒数、開始時の見積もり | 開始前の完了から推定した作業時間 |

スヌーズはWeb・拡張とも`/draft/commit`へ操作種別を渡し、サーバーで保存成功した場合だけ記録する。課題名の変更やAIへの相談はスヌーズに数えない。

現在の一時停止APIはトグルなので、通信再送で反対の状態になる可能性がある。新クライアントは`PUT /api/session/pause`に`{paused: true/false, requestId}`を送り、結果の再取得・再送が同じ状態に収束するようにする。旧POSTは互換期間だけ維持し、自動再送の対象にしない。

記録は操作・残高等の更新と同じFirestoreトランザクションで保存する。クライアント時計は実績の根拠にしない。イベントの保持を画面の表示期間で切り捨てない。

記録画面には週別の完了件数、開始のずれ、確定スヌーズ回数、見積もりとタイマー上の作業時間を表示する。週はプロフィールのタイムゾーンで月曜始まりとし、境界の計算を共通化する。開始のずれは開始時点に記録した予定から算出し、後日の予定変更で過去の値を変えない。

新機能の開始前は未計測と表示し、0回・0分で埋めない。ブラウザーの終了・スリープ中も現タイマーは経過し得るため、「集中時間」と呼ばない。新たな自動停止や就寝操作は追加しない。AIによる見積もり改善は、計測可能な記録が蓄積してから本人確認付きの提案として加える。

変更箇所：開始・完了・一時停止・draft確定API、`shared/models.ts`、Web/拡張の送信、⑤の記録API、`records.*`・`activity.ts`。⑦のリリース前に発生していない操作を生成しない。
