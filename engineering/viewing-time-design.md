# 視聴時間の付与を、自己管理の練習につなげる

2026-11-07。**検討案・未実装**。初回1時間、ログインボーナス、1時間ごとの付与を比較し、自分で視聴と作業を切り替えられる状態を目指す設計案。数値は試用の開始値であり、最適値や健康上の推奨時間ではない。

## 目指す変化

「予定した時刻に作業へ移れる」「自分で決めたところで視聴を終えられる」「アプリの介入を減らしても続けられる」を目指す。視聴時間、課題登録数、ログイン日数だけを成果にしない。

[企画の概要](../concept/00_overview.md)にある「最後はアプリがなくても自分で管理できる」を、この検討の判断軸として使う。企画資料の古い実装対応表は現状の根拠にせず、以下はコードで確認した。

## 現状と、先に変えたい点

| 項目 | 現在のコード | 目標との関係 |
|---|---|---|
| 初回 | 60分を1回付与 | 作業を始める前に長く視聴できる。習慣改善に適切な量かは未評価 |
| 新規課題の登録 | 1件10分 | 計画を促せる一方、登録だけで視聴枠を増やせる |
| 課題の完了 | 1件20分 | 作業時間・開始の有無によらず同額。課題を細分化すると増えやすい |
| 残高 | 繰り越し可能、上限なし | 何時間分も蓄積できる。獲得量と当日に使う量が分かれていない |
| 消費 | 前面で再生中のShortsを計測、ゼロで一時停止 | 自分で終了時刻を決める練習は別に必要 |
| 重複 | 同一課題・同一種類の再送による付与を防止 | 別IDの課題作成による付与までは防がない |

例えば初日に2件登録して2件完了すると、消費前の付与合計は **60＋2×10＋2×20＝120分**。これは計算例であり、実ユーザーの観測値ではない。初回だけ減らしても、登録・完了の仕組みから再び大きく増える。

確認箇所：[初期残高と付与](../api/internal/app/model.go)、[登録・完了・視聴API](../api/internal/app/server.go)、[Calendar登録](../api/internal/app/calendar.go)、[Shorts計測と停止](../extension/src/content.ts)。

## 付与方法の比較

以下の行動への影響は、DOPAGAKIで未検証の設計仮説。

| 案 | 利点 | 気になる行動 | 判断 |
|---|---|---|---|
| 初回60分 | 制限の負担が小さく、試しやすい | 最初の切り替えを経験する前に長く視聴する | 標準候補は10〜15分。普段の利用量によって調整 |
| ログインすると毎日付与 | 分かりやすく、毎日戻る動機になる | 用事がなくても受け取りに来る。連続ログインの維持が目的になる | 受取ボタン・連続日数による増額を設けない |
| 1時間ごとに付与 | 使い切っても待てば再開できる | 次の回復を待つ、残高を何度も確認する | 最初の候補から外す |
| 毎日の少量補充 | 課題のない日も短く楽しめる | 日替わり直前・直後のまとめ見 | 初回と重ねず、1回の枠も別に設ける |
| 作業後に付与 | 作業への切り替えを後押しできる | 視聴を稼ぐための作業・虚偽完了・報酬への依存 | 少額・上限付き。将来は本人の選択で弱める |
| 本人が決める固定枠だけ | 説明が簡単で、報酬稼ぎが起きない | 作業開始の後押しが弱いかもしれない | 作業報酬付きの案と比較する価値がある |

例えば1時間ごとに5分なら、16回の補充で80分になる。回復間隔だけでなく、1日の総量を決める必要がある。回復通知・カウントダウンは設けない。

## 最初に試す案

**少量の毎日補充＋作業後の少額追加＋見る前の区切り。** 次の数値を一緒に固定仕様へせず、試用して調整する。

| 項目 | 開始値の案 | 意図 |
|---|---|---|
| 初回 | 10分 | 最初の短い視聴と切り替えを体験する。当日の毎日補充分を含む |
| 毎日の補充 | 残高が10分未満なら10分まで補充 | ログイン操作に報酬を付けず、未使用日をため込まない |
| 課題登録 | 視聴時間は増やさない | 「予定が決まった」「最初の一手が決まった」を成功表示にする |
| 作業後の追加 | 確認した作業5分につき視聴1分、1日最大20分 | 25分なら5分。小さな作業も合算し、課題数では増えない |
| 残高の上限 | 30分 | 作業分も含め、無制限に蓄積させない |
| 1日の視聴上限 | 30分 | 繰り越しと当日の追加で上限を超えない |
| 1回の視聴 | 開始前に5分か10分を選ぶ。残高・当日残枠以下 | 「残高がある限り見る」から「決めた長さで終える」へ |
| ログイン・時間経過 | 追加なし | 残高確認そのものを日課にしない |

毎日補充は「毎日10分を加算」ではない。前日の残高が4分なら6分補充、15分なら補充なし。追加で得た時間も上限内で繰り越し、日替わりに没収しない。使い切りを促す通知や「今日で失効」は出さない。

初日10分、再ログインで追加0分。作業25分の確認で5分増えて残高15分。10分見たら残高5分、翌日は10分まで補充される。5分未満の作業端数は当日内で合算する。課題を5件に分けても、確認した作業の合計が同じなら追加量は同じ。

これは1日30分を万人に課す提案ではない。開始時に本人が普段の利用量と目標を選び、急に厳しくして外してしまう場合は、20分・30分などの初期枠も比較する。選んだ設定は常に見られ、変更は本人が確認する。

### 作業時間をどう扱うか

- タイマーが終わっただけでは付与しない。「ここまで取り組んだ」と本人が確認した区間を対象にする。課題全体が未完了でも、小さく取り組めるようにする。
- 一時停止を除き、事前に決めた作業区間の長さを上限にする。放置した一晩をそのまま報酬に変えない。
- 端数を含む確認済み作業量を日単位で合算し、評価済みの区間を再評価しない。残高・日次付与上限で増やせない分は後から自動で付与しない。
- 現行の`Session`は経過時間であり、実作業の証明ではない。この案も本人の申告を含む。監視や操作回数の収集で証明しようとしない。
- 累計時間での付与は現行の「課題完了で20分」より実装が増える。最小変更で試す場合は「完了で5分・1日3回まで」を代替案にできるが、課題の細分化で増える性質が残るため、同じ案として評価しない。

### 視聴を終えるとき

開始前は「今日はあと15分。今回は5分にする／10分にする／今は見ない」。終了時は一時停止し、「ここで終える／次の作業へ／残り枠からもう5分」を示す。延長は日次上限内で明示的に選び、回数を記録する。延長を許すため、1回10分は強制的な連続視聴上限ではない。

区切りで終えたことを静かに記録する。終了できた報酬として視聴時間を増やすと、終えるために何度も開く動機ができるため、そこには時間を付けない。作業後もShortsを自動で開かず、「休む／散歩する／Shortsを5分見る」を本人が選べるようにする。

## 卒業へのつなぎ方

成功を連続ログインや視聴残高の多さで表さず、「予定した時刻に始められた」「決めた区切りで終えられた」を週単位で振り返る。失敗した日の没収、借金、連続記録のリセットによる罰は入れない。

本人が安定したと感じたら、**作業に応じて時間が増える方式 → 本人が決める固定枠＋区切り → 通知だけ → 自己管理**を選べるようにする。卒業で急に利用枠が減らないよう、固定枠は本人と決める。通知の強さと報酬率は同時に変えず、困ったら前の段階へ戻せる。移行に必要な日数や成功率はまだ決めない。

## 効果の確かめ方

最初は参加者ごとに普段の3〜7日と、候補案の7〜14日を記録する。少人数の前後比較は使いにくさと傾向の発見に使い、因果効果とは呼ばない。普段の期間のために新しく60分の付与を受けさせる必要はない。

| 見るもの | 定義と注意点 |
|---|---|
| 決めた区切りで終了できた割合 | 終了予定後60秒以内に視聴を止め、次の5分は再開しなかった回／終了予定を迎えた回。時刻の幅は試用上の定義 |
| 作業への切り替え | 予定開始から実際の開始までの遅れ。未開始も別に数え、開始できた課題だけで改善を主張しない |
| 意図しない視聴 | その日の「予定より見てしまった」という短い本人の振り返り |
| 副作用 | 延長回数、残高確認の増加、拡張の無効化・利用中断の申告、他端末への移動の申告、窮屈さ |
| 補助指標 | 計測できたShorts視聴分数、課題の完了。ログイン数は成果指標にしない |

現行コードには視聴セッションごとの予定終了・延長・区切りの結果を残す仕組みがなく、消費は残高に反映するだけで`Ledger`にも記録していない。上記の評価には追加の記録が必要。動画URLや内容を保存せず、必要な時刻・秒数・操作だけを本人に説明して扱う。記録がない日を視聴ゼロや成功にしない。スマホや他ブラウザーの利用は計測範囲外。

まず「初回10分と20分」を比較するなら、以後の補充・報酬・区切りは同じにする。次に同じ日次上限・区切りで「作業追加あり／固定枠だけ」を比べる。複数の仕組みを一度に変えた結果から、どれが効いたかを断定しない。参加者が増えたら割当を無作為化し、曜日・順序・習慣の持ち越しも考慮する。

## 研究から借りること、まだ分からないこと

- Allcott, Gentzkow, Song（2022）, [Digital Addiction, American Economic Review](https://www.aeaweb.org/articles?id=10.1257/aer.20210867)：本人が将来の利用上限を設定できる介入で利用減少を報告している。「本人が枠を決める」設計の参考。Shortsを作業報酬にすることや、10分・30分という量の根拠ではない。
- Grüning, Riedel, Lorenz-Spreen（2023）, [Directing smartphone use through the self-nudge app one sec, PNAS](https://pmc.ncbi.nlm.nih.gov/articles/PMC9974409/)：対象アプリを開く際の介入を調べ、オンライン実験では消費をやめる選択肢が最も強く働いた。「今は見ない」を用意する参考。開発者が著者に含まれ、DOPAGAKIの視聴途中の停止と同じ介入ではない。

初回60分が多すぎるか、定期付与が再訪を増やすか、作業報酬が自立を助けるかは、この製品では未検証。ここでは設計仮説として扱う。

## 採用する場合の実装範囲

1. APIに付与方針の版、日付、補充済み状態、当日の消費・付与・確認済み作業量を持たせる。サーバー時刻と本人の設定タイムゾーンで日付を決める。境界・タイムゾーン変更・オフライン復帰で二重補充しない扱いを決める。
2. Firestoreトランザクション内で補充・消費・作業確認を行う。毎時のジョブは不要で、認証した状態取得・更新時に当日分を適用できる。休んでいた日数分は加算しない。
3. 手入力・AI相談・Calendar同期・デモの登録付与を統一して止める。完了付与を新しい作業確認へ移し、残高が上限に近い場合は実際の増分を表示する。
4. 拡張へ「今回の枠」を追加し、複数タブ・再読み込みでも維持する。UI・通知・記録に散らばる「登録＋10分」「完了＋20分」を合わせる。
5. 再送・同時操作・日替わり・タイムゾーン変更・休止日・作業端数・課題分割・上限・日替わりをまたぐ作業と視聴・未接続時の扱いを回帰確認する。現在の`Session`だけでは日別配分を復元できない場合があるため、区間の記録方法も決める。

既存利用者の残高を突然30分へ切り捨てない。初回の試用は新しいデモ利用者から始め、既存残高を残しつつ新しい日次上限を適用する移行は本人への説明と選択を別途設計する。

この設計案に伴うアプリの挙動変更、利用者データの変更、デプロイ、効果測定は行っていない。
