# 開発で得た知見：2026-11-06

対象：DOPAGAKIのGoogle連携設定、Cloud Run配信、実サービス確認。確定した原因と、原因を確定できていない観測を分けて残す。

## 1. ログインの待機と初期データ取得を、同じ操作ロックで止めない

**症状**：Googleログインが終わっても、管理画面の内容が空になることがあった。再読み込み後には表示された。

**原因**：ログイン処理が `busy` を保持している間に `onIdTokenChanged` が発火し、同じ `run()` を使う初期データ取得が「処理中なので実行しない」となった。認証済みという状態だけが進み、データが未取得のまま残った。

**対処**：認証状態の通知では操作ロックを経由せずにデータを取得し、初回通知の処理が終わるまで初期化を待つ。読み込み表示と、操作の二重送信防止を分けた。設定画面にはログイン中のメールを表示し、接続先を確認できるようにした。

**確認**：別のChromeプロフィールから新規ログインし、再読み込みで回避せずに課題と残高が出ることを実サービスで確認した。

根拠：[api.ts](../web/src/app/api.ts)、修正コミット `3f33f90`。学びは、非同期処理を一律に `busy` で囲めば安全になるわけではなく、初期化が必ず完了する経路を確保すること。

## 2. Google Chatは、実際に作るアプリの形式から確認する

**症状**：当初の実装は、従来のChatイベントと共通の送信元サービスアカウントを想定していた。実際の設定画面ではWorkspaceアドオン形式になっており、そのままでは一致しなかった。

**対処**：現在のアプリ設定に合わせて次の3点を変更した。

| 項目 | 現在の実装 |
|---|---|
| 受信 | `chat.user`、`chat.messagePayload.message` |
| 応答 | `hostAppDataAction.chatDataAction.createMessageAction.message` |
| 送信元 | プロジェクト専用SA。署名、HTTPエンドポイントのAudience、`email_verified`、メールを検証 |

プロジェクト番号を `GOOGLE_CLOUD_PROJECT_NUMBER` に設定した。Calendar接続時に保存したGoogle IDとの対応から利用者を特定する。

根拠：[chat.go](../api/internal/app/chat.go)、コミット `3f33f90`。[Googleのイベント説明](https://developers.google.com/workspace/chat/receive-respond-interactions)、[リクエスト検証](https://developers.google.com/workspace/chat/verify-requests-from-chat)。仕様の一般論だけでなく、今回の設定画面・アプリ形式・本番受信を照合した。

## 3. 公式SDKの型でも、別の配信形式のJSONを丸ごと読めるとは限らない

**症状**：Chat側で「応答がありません」と表示された。Cloud Runは400、処理時間は約0.009秒だった。AIの応答待ちが原因とは考えにくい観測だった。

**調査**：本文をログへ出さず、JSONの読み取りエラーを記録したところ、次の原因が分かった。

```text
json: cannot unmarshal number 1.0 into Go struct field
chatEvent.chat.messagePayload.message.space.membershipCount.joinedDirectHumanUserCount
of type int64
```

実イベントの人数メタデータは `1.0` だった。一方、メッセージ全体の読取に流用していたChat REST SDKの該当フィールドは整数型だった。課題登録には使わない項目のために、必要なメッセージまで拒否していた。

**対処**：イベントの受信型を、利用者名、メッセージ名、本文等の必要な項目に限定した。数値変換の独自処理や、すべてを無型のmapにする処理は増やさなかった。

**回帰確認**：不要なメタデータに `1.0` を含むfixtureを追加し、必要項目の読み取りとアドオン形式の応答を確認した。その後、実Chatで登録・返信、Calendarの詳細欄、登録報酬まで確認した。

根拠：[chat_test.go](../api/internal/app/chat_test.go) の `TestWorkspaceChatMessageContract`、コミット `d523947`。教訓は「SDKを避ける」ではなく、APIクライアントの型と、別の経路で届くイベントの契約を区別すること。

## 4. Chromeのプロフィール、Googleアカウント、拡張の設置先は別に確認する

**症状**：Shortsの動画は再生されているのに、視聴時間が減らなかった。

**原因**：拡張は個人用Chromeプロフィールへ追加され、確認用Shortsは別のプロフィールで開いていた。さらに、Webアプリのログイン先も、ブラウザーの既定アカウントから推定してしまった。

**対処**：利用者が指定した個人アカウントに統一した。公開アプリとShortsを、拡張が入った同じChromeプロフィールで開いた。GoogleのCalendar同意画面でも対象アカウントを確認し、連携レコードを照合した。

**確認**：ログイン、拡張との接続、Shortsの計測、通知まで通った。ブラウザー上で同じサービスが開けることだけでは、同じプロフィールで動いている証拠にならない。

設定・再現時には、①アカウント、②Chromeプロフィール、③拡張の入ったプロフィール、④公開先オリジン、を先にそろえる。

## 5. 「動画が再生中」と「視聴時間の計測条件を満たす」は異なる

**観測**：動画要素が `paused=false`、再生可能な状態でも、Chromeが前面でなければ残高は減らなかった。前面に出すと減算された。

**実装**：表示状態、フォーカス、ShortsのURL、動画の再生状態、通知の有無を組み合わせる。拡張のバックグラウンド側でも送信元タブ等を確認する。

**実確認**：登録2件後の4,800秒から、前面再生と報告の反映後に4,750秒となった。途中では4,790秒、4,772秒を観測した。一時停止後、送信済み報告が反映された状態で4,750秒が変わらないことを確認した。

視聴報告はまとめて送るため、UI表示やサーバー値を1回見ただけで秒単位の即時性を断定しない。これは1回の操作試験であり、長期間の計測精度や複数端末での精度評価ではない。

根拠：[content.ts](../extension/src/content.ts)、[background.ts](../extension/src/background.ts)、[検証記録](verification-2026-11-06.md)。

## 6. 確定後の時間と、元の見積もりを混ぜない

**症状**：元の見積もり20分の課題を、確認後は2分の予定に短縮した。通知と作業バーは2分を使う一方、ホーム画面には20分の作業と出ていた。

**原因**：表示箇所によって `task.minutes` と確定した予定の長さを使い分けてしまっていた。

**対処**：実行する作業時間は `plannedSeconds` / `plannedMinutes` から表示する。一覧では「予定」と「見積もり」を区別する。

**回帰確認**：E2Eで30分の課題を10分へ変更し、次の課題、一覧の元の見積もり、タイマーの10分表示を照合した。実環境でも短縮後の2分タイマーを確認した。

根拠：[shared/models.ts](../shared/models.ts)、[app.html](../web/src/app/app.html)、[app.spec.ts](../tests/e2e/app.spec.ts)、コミット `d523947`。

## 7. ローディングのテストは、短い固定待ち時間に依存させない

**症状**：失敗応答を350ms遅らせて処理中表示を確認する試験が、負荷のある実行で失敗した。確認前に応答が返り、「処理中」のボタンが消えたためだった。

**対処**：HTTP応答をPromiseで保留し、処理中ボタンが無効であることを確認してから応答を解放する。失敗表示と入力保持も確認する。

根拠：[app.spec.ts](../tests/e2e/app.spec.ts) の `failed registration preserves input and loading state`。コミット `d523947`。ローディングの存在を試験する際は、見せたい状態をテストが制御する。

## 8. 通知前の準備と、保存後の成功表示を分ける

通知からスヌーズを押したときに、ネットワークやAIを待つ時間を減らすため、事前候補を状態へ含めた。確認中は候補のコピーを編集し、OKでのみ保存する。保存が成功する前には成功表示しない。

実環境で、確認画面を編集している間の確定開始時刻が変わらないこと、OK後には開始時刻とCalendar詳細欄が変わることを確認した。候補を事前に用意したことによる待ち時間短縮の平均値は測っていない。

根拠：[server.go](../api/internal/app/server.go) の `prepareDraft`、[plan-dialog.ts](../web/src/app/plan-dialog.ts)、[content.ts](../extension/src/content.ts)。

## 10. 拡張をどのオリジン向けにビルドしたかを確認する

**症状**：ローカルの拡張E2Eで接続できなかった。

**原因**：`dist/extension` が公開Cloud Run向けのビルドになっていたのに、テストはlocalhostの管理画面へ接続しようとしていた。

**対処**：ローカル向けにビルドし直して拡張E2Eを通し、その後、公開先URLを指定して配布用を作り直した。最終ZIPも公開先向けに更新した。

通常の `npm run build` も拡張をlocalhost向けにビルドする。既存の `dist/extension` が配布用のままとは限らない。`manifest.json` の接続先を確認する。開発版と配布用の出力先を分けることは、今後の改善候補であり未実装。

根拠：[build-extension.mjs](../scripts/build-extension.mjs)。

## 11. Google Calendarでは自分の書き戻しも変更通知になる

カレンダーに具体的な手順を書けば、その書き込みも同期対象になる。詳細欄全体を入力変更として比較すると、再具体化や書き戻しを繰り返す原因になる。

現在は元のメモとDOPAGAKIブロックを分け、入力ハッシュからブロックを除外する。既存メモの保持、編集・再送・削除の扱いを単体テストで確認した。実サービスでは、カレンダー側の新規登録、Geminiからの登録、詳細欄への反映、既存予定の更新で報酬が増えないことを確認した。

Google CalendarとFirestoreの原子的な一括更新は実装していない。外部書き戻しの失敗は `pending` と再同期で扱う。

根拠：[calendar.go](../api/internal/app/calendar.go)、[calendar_test.go](../api/internal/app/calendar_test.go)。

## 12. Cloud BuildのDockerで使える構文を確認する

**症状**：診断用イメージのビルドで `COPY --chmod=755` が失敗した。

**原因**：そのビルドはBuildKitではなく、次のエラーになった。

```text
the --chmod option requires BuildKit.
```

**対処**：Goが作成した実行可能ファイルのモードをコピー元で保ち、通常の `COPY` を使った。今回のためだけにビルド方式を広げなかった。その後のCloud Buildは成功した。

現行の [Dockerfile](../Dockerfile) はこのオプションを使っていない。

## 13. ツールや実行環境の失敗を、アプリの失敗と混同しない

| 観測 | 実際の対応・結論 |
|---|---|
| ローカル `httptest` がポートをlistenできなかった | サンドボックスの制限だった。許可された実行環境で同じ試験を実行し成功。HTTPコードを変更して回避していない |
| ローカルAngularビルドが異常終了した | 通常の実行環境では成功。これだけでAngularの不具合やアプリの原因と断定していない |
| Google APIが有効なのに、一部のCLI一覧操作が無効と表示した | 対象プロジェクト・リージョン・課金先を明示した操作とRESTでは進められた。最初の表示の根本原因は未確定 |
| GitHubへのpushが `commit_refs_rules` の内部エラーで拒否された | ブランチ保護を変更せず、通常のpushを再試行して成功。ルール設定の問題だったとは断定していない |
| ブラウザー自動操作で管理画面を扱えなかった | 拡張追加等は本人操作を依頼した。アプリ側の導入失敗とは区別した |

## 14. Cloud Runへの公開と、個人データAPIの認証を分ける

Cloud Run自体は公開し、GoogleのWebhookや静的画面を受け付ける。個人データのAPIはFirebase認証、ChatはGoogleの署名とAudience、監視更新は専用のBearer値で保護する。

実際に `/api/health` は200、未ログインの `/api/state` は401を確認した。これだけで全エンドポイントの安全性を証明したとは言わない。利用者間の分離や再送の挙動は、別の単体テストで確認している。

Cloud Run、Firebaseの許可オリジン、OAuth、拡張の接続先は、同じ正式公開URLへそろえた。URLを持つだけで連携が完成するわけではない。
