## 1. 木村さんが作ったもの（全体像）

| 部分 | 中身 |
|---|---|
| 管理画面 | Angular。課題の登録、予定の確認、記録（草）、設定、「作業の傾向」の入力 |
| Chrome 拡張 | Shorts の再生を測って持ち時間から減らす。開始時刻の全画面通知、スヌーズの確認画面、作業中の細いバーとタイマー |
| API | Go。認証、予定の検証、持ち時間の計算、各 Google サービスとの連携 |
| AI | Vertex AI の Gemini。①文章から課題を取り出す、②課題を1〜8個の手順に分ける、③スヌーズ候補を指示どおりに直す |
| 入口 | 3つ：管理画面、Google カレンダー（専用の DOPAGAKI カレンダー。Gemini アプリから予定を入れるのも可）、Google Chat |
| 実環境 | Cloud Run（東京）で公開済み。Calendar・Chat・実際の Shorts での動作も確認済み |

### 設計の特徴（意味づけに使える点）

| 実装の判断 | 意味づけ |
|---|---|
| **AI は提案だけ。時間・締切・重複の検証、持ち時間の計算はプログラムが行う** | 「AI に決めさせない」を、仕組みの段階で守っている。AI の出力（JSON）は型を決めて受け取り、合計時間が合わなければ捨てる |
| **スヌーズは、変更前後を見て本人が OK を押すまで確定しない** | 本人の主導権（P6）。押しつけない |
| **完了の報酬は本人が押したときだけ。タイマーが終わっただけでは与えない** | 自分で「やった」と認める練習（セルフモニタリング） |
| **スヌーズの候補は通知の前に作っておく** | 迷う時間を短くする＝「ひと手間」は入れるが、余計な待ち時間は入れない |
| **「作業の傾向」**（得意・苦手、進め方）を本人が書き、Gemini が手順作りの参考にする | 自分の特性を言葉にする＝認知行動療法の心理教育（自分を知る）に当たる |
| **閲覧中の動画の内容・閲覧履歴は AI に送らない** | プライバシー（P10） |
| 前面で再生している Shorts だけを測る（バックグラウンド・一時停止は数えない） | 「見た時間」を正直に測る |
| 新しい課題の登録で＋10分 | 「始める前の一歩（登録＝計画）」にもご褒美。計画すること自体を強化 |

## 2. Google の技術（採点 1a・1b）

| 技術 | 使い方 | 採用理由（1b で言えること） |
|---|---|---|
| **Gemini（Vertex AI、Google Gen AI SDK for Go）** | 課題の抽出、手順への分解、スヌーズ候補の調整。出力の形（スキーマ）を指定して受け取る | あいまいな課題を、具体的な手順と時間に変えられる。形を決めて受け取り、プログラムで検証できる |
| **Google Calendar API** | 専用カレンダーの作成、予定の書き込み、変更の通知（プッシュ通知）と差分の取得 | 「いつやるか」を先に決める（実行意図）。毎日見る予定表に置くのが一番自然 |
| **Gemini アプリ** | 「DOPAGAKI カレンダーに入れて」と話しかけるだけで課題が入る | 思いついたその場で、一言で登録できる |
| **Google Chat** | Chat アプリに課題を送ると登録され、返事が来る | 普段使う連絡の場から、手間なく登録できる |
| **Firebase Authentication** | Google アカウントでログイン | — |
| **Firestore** | 利用者ごとの状態をトランザクションで保存 | 持ち時間を二重に増やさない、競合を防ぐ |
| **Cloud Run** | 管理画面と API を同じ場所で配信 | 使わないときは0台まで縮む。費用が小さい |
| **Secret Manager** | OAuth の秘密情報、利用者ごとのカレンダーのトークン | 秘密情報をコードや設定ファイルに置かない |
| **Cloud Scheduler** | カレンダーの変更通知を毎日更新 | — |
| **Cloud Build、Artifact Registry** | コンテナーの作成と保管 | — |
| **Chrome 拡張（Manifest V3）** | Shorts の上で通知・計測・タイマー | ブラウザーの中、まさに見ている場所で働ける |
| Go、Angular、Material Design | API の言語、管理画面の枠組み、見た目の部品 | いずれも Google 発のオープンソース。**中核として数えるのは上の Gemini・Calendar・Firebase・Cloud Run など**で、こちらは補足として触れる程度にする |

**1a で強く言える点**：入口（Gemini アプリ・Calendar・Chat）から、頭脳（Gemini）、置き場所（Calendar・Firestore）、実行基盤（Cloud Run）まで、**流れの全部が Google の上でつながっている**。

## 3. 要件ごとの対応

◎＝実装済み ／ ○＝ほぼある（小さな直しで足りる） ／ △＝一部だけ ／ ×＝未実装

| ID | 要件 | 状況 | 実装の中身と差分 |
|---|---|---|---|
| F1 | 課題の登録（画面・カレンダー・会話） | ◎ | 3つの入口すべて実環境で確認済み |
| F2 | **Why の入力** | × | 課題には「メモ」欄だけ。**Why の欄がない**。いちばん大きな差分 |
| F2+ | 障害と if-then（E2.2 の提案） | × | なし |
| F3 | 手順への分解 | ◎ | Gemini が1〜8段階に分け、合計時間をプログラムで検証。本人の「作業の傾向」を参考にする |
| F4 | 逆算した予定とカレンダー | ◎ | 締切から逆算し、複数の課題も重ならないよう並べ直す。カレンダーの詳細欄に手順を書き戻す |
| F5 | 開始の通知（Why と最初の一手） | ○ | Shorts を止めて全画面で出す仕組みはある。**出しているのは「課題名・作業の分数・完了で＋20分」**。Why も、最初の一手（手順の1行目）も出していない |
| F6 | 「閉じる」と「始める」 | △ | ボタンは「作業をはじめる」「スヌーズ」「予定を調整する」「閉じる」。**ただし今の「閉じる」は通知を閉じて Shorts に戻るだけ**。one sec の研究で効いたのは「**見るのをやめる**」選択肢なので、意味が逆になっている |
| F7 | スヌーズと立て直し | ◎ | 候補を事前に作り、変更前後を見せ、OK で確定。Gemini への指示でも直せる。間に合わない場合は短縮案と明示 |
| F8 | 作業中は静かに | ◎ | 上端の細いバーとタイマー、一時停止・再開 |
| F9 | 持ち時間 | ◎ | 初回60分、登録＋10分、完了＋20分。**持ち時間がゼロになると Shorts を止める** |
| F10 | 記録（草） | ◎ | 完了の履歴を草のカレンダーで表示。持ち時間の増減の履歴もある |
| F11 | **フェーディング** | × | なし。逆に、完了が途切れると画面の角が少しずつ暗くなる演出（初期値オン）がある |
| F12 | 振り返りの数字 | △ | 完了の履歴と持ち時間の履歴はある。**スヌーズの回数、予定どおりに始めたかは記録していない**。週の振り返りの画面もない |
| F13 | 夜の扱い | × | なし |
| F14〜F18 | 将来の展開 | × | 構想のみ（予定どおり） |
| 非機能：プライバシー | ◎ | 閲覧履歴を AI に送らない。Firestore は API からしか触れない |
| 非機能：音・動き | ◎ | 音のオン・オフ、動きを控える設定あり |

## 4. 理想形とぶつかっている点

| 実装 | ぶつかる原則 | 提案 |
|---|---|---|
| 通知の演出が「パチンコ」（初期値）と「麻雀」（見出しが「作業、ツモ。」） | 医療・福祉の筋。やめられない仕組みを「ギャンブルと同じ構造」と説明している（根拠 B）のに、演出がギャンブル | 名前と見出しを変える（例：「お祭り」「金色」）。演出の派手さはそのままでよい |
| 「閉じる」＝通知を消して Shorts に戻る | P5 | 「閉じる」を「**Shorts をやめて始める**」の意味にする。通知だけ消すボタンは「あとで」などにする |
| 持ち時間ゼロで Shorts を止める | P1「禁止しない」 | 実装はそのままでよい。説明を「本人が自分で入れ、いつでも外せる、**自分で決めた上限**」にする（Allcott 2022：自分で決めた制限には効果がある） |
| 完了が途切れると画面が暗くなる（初期値オン） | P9「責めない」 | 初期値をオフにするか、「暗くなる」ではなく「続いた日が明るくなる」方向にする |
| 製品名 DOPAGAKI | 9章 言葉の使い方 | 保留中（未決事項） |

## 5. 意味づけに反映できる点（資料・動画に足す）

1. **「AI は提案、決めるのは本人、守るのはプログラム」の三段構え**
   AI の出力をそのまま使わず、プログラムで検証し、最後に本人が OK を押す。テーマ "Own the Why" を**設計の構造**として説明できる。1b（採用理由）の答えにもなる
2. **「作業の傾向」は、自分を知る練習**
   得意・苦手を本人が言葉にし、Gemini がそれに合わせて手順を作る。認知行動療法の心理教育（自分の特性を知る）に当たる
3. **登録だけでもご褒美（＋10分）**
   「始める前に計画する」こと自体を強化している。先延ばしの最初の壁（手をつける）を低くする
4. **入口が3つある＝始める手間を最小にする**
   思いついたその場（Gemini アプリ、Chat）で登録できる。「あとで登録しよう」で止まらない
5. **持ち時間ゼロでの停止は「自分で決めた上限」**
   禁止ではなく、本人が選んだコミットメント（Allcott 2022）

## 6. 木村さんへの依頼候補（優先順）

| 順 | 変更 | 規模の目安 | 効く採点項目 |
|---|---|---|---|
| 1 | 課題に **Why** の欄を足し（任意入力）、通知に1行で出す | 小 | テーマ、3b |
| 2 | 通知に**手順の1行目（最初の一手）**を出す | 小 | 3b |
| 3 | 「閉じる」の意味を「Shorts をやめて始める」に変える | 小 | 3b（one sec の根拠と一致） |
| 4 | 演出の名前を変える（パチンコ・麻雀） | 小 | テーマ、カテゴリの筋 |
| 5 | スヌーズの回数と「予定どおりに始めたか」を記録する | 中 | 3b（4人の試用のデータ） |
| 6 | フェーディング（続いたら通知を弱める） | 中 | テーマ（卒業）、3b |
| 7 | 障害と if-then の欄（F2 の拡張） | 小〜中 | テーマ |
| 8 | 夜の扱い | 中 | 医療・福祉の筋 |

1〜4 は表示の変更が中心で、締切（11/10 19:00）までに入れやすい。5 は試用のデータを取るために、**試用を始める前**に入っている必要がある。
