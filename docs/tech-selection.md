技術設計書 2章の技術スタックについて、技術ごとに選んだ理由、捨てた案、弱点と対策を書く。プロダクト説明ドキュメントの「選定理由」はここから書く。

---

## 1. 画面：Angular

**選んだ理由**

- Google が開発しているフレームワークで、採点の「Google 技術」で説明できる。
- Angular チームが作る公式の地図部品 `@angular/google-maps` があり、Google マップの上に避難所、避難者、経路を重ねる画面を、地図部品を自分で包まずに作れる。
- 画面は自治体や施設の職員が使う業務画面で、検索エンジンに載せる必要がない。サーバー側で画面を作る仕組み（SSR）が要らないので、ビルドした静的ファイルを配るだけで済む（8. 実行基盤につながる）。
- TypeScript なので、API の OpenAPI から生成した型をそのまま使える（9. 型の共有）。

**捨てた案**

- Flutter Web：Google 製で、スマートフォン対応（NFR-002）も同じコードで済む。しかし Web で地図に多くの図形を重ねる画面は、Angular と公式地図部品の組み合わせより手間がかかる。
- Next.js、React（Vite）：書ける人が多いが Google の技術ではなく、採点の「Google 技術」の説明に使えない。Next.js の強みである SSR も今回は使わない。

**弱点と対策**

- 決まりごとや設定ファイルが多く、小さな画面でも書く量が増える。画面数を要件定義書の SC-001〜007 に絞る。

## 2. 地図：Maps JavaScript API（2D）

**選んだ理由**

- Google マップそのものを画面に埋め込める。職員も住民も普段から使っている地図なので、見方を説明しなくてよい（NFR-003、NFR-004）。
- 避難所や避難者の印、経路の線を重ねる機能が最初からある。
- 1. の `@angular/google-maps` から使える。

**捨てた案**

- Photorealistic 3D：動画では目を引くが、地図の料金と実装の手間が増える。要件定義書でも 3D は「拡張」（FR-025）なので、2D で完成させてから考える。
- deck.gl の重ね描き：人の流れを色や線の太さで見せられるが、MVP には要らない。

**弱点と対策**

- 地図の読み込みは課金の対象になる。API キーに、使える API と使えるサイト（HTTP リファラ）の制限をかける。無料で使える量は未確認。

## 3. API：Python と FastAPI

**選んだ理由**

- 最適化を OR-Tools の Python 版で書くため、API も Python にそろえる。最適化の定式化を書く人が、API までそのまま触れる。
- FastAPI は入出力を Pydantic の型で書く。同じ型を、Gemini に返させる JSON の形の指定（構造化出力のスキーマ）にも使える。「API が受け付ける形」と「Gemini が返す形」が1か所の定義にそろう。
- FastAPI は OpenAPI の仕様を自動で出すので、Angular 側の型を生成できる（9. 型の共有）。

**捨てた案**

- Flask：小さく単純だが、入力の型検査を自分で書く必要がある。
- Functions Framework：Google 製で関数を並べるだけで動くが、API が増えると整理しにくい。

## 4. 最適化：OR-Tools

**選んだ理由**

- 問題は「避難所の割り当て」と「配車」の2つに分かれ、OR-Tools にはどちらにも専用の道具がある。Google の技術でそろえられる。
- 避難所の割り当ては、「誰をどの避難所へ」を 0/1 の変数で表し、収容人数と配慮の条件を制約にする。整数だけの問題なので、OR-Tools の CP-SAT で解く。
- 配車（誰をどの車でどの順に運ぶか）は、OR-Tools のルーティングライブラリで解く。車の定員、迎えに行って避難所で降ろす組み合わせ、時間枠を最初から扱える。
- ライブラリなので呼び出しごとの料金がかからない。$20 で 11/14 まで動かす制約に合う。
- 小さな入力を手元で作り、制約が守られているかをテストで確かめられる（[技術設計書](design.md) 7章）。

**捨てた案**

- Route Optimization API：Google Maps Platform の配車 API で、配車には強い。しかし呼び出しごとの従量課金で、$20 では計画を作り直すたびに残額を気にすることになる。収容人数つきの避難所割り当ても書きにくい。
- HiGHS：力を発揮するのは連続変数の多い LP や MIP で、整数だけの割り当て問題では利点がない。配車まで MIP で書くと変数が一気に増え、60 秒（8. の Hosting のタイムアウト）に収めるのが難しくなる。Google の技術でもない。
- 貪欲法の自作：一番速く作れるが、最適さを説明できない。制約違反を見つける処理も別に書く必要がある。

**弱点と対策**

- 割り当てと配車を順に解くので、2つをまとめて解いた場合より悪い計画になることがある。まとめて解くと時間内に終わらなくなるため、順に解くことを選んだ。この点はプロダクト説明ドキュメントにも書く。

## 5. AI：Gemini（Flash 系）を Vertex AI 経由で

**選んだ理由**

- 任せるのは、配慮情報の読み取り（決まった項目への構造化）と、計画の短い説明文の2つだけ。どちらも Flash 系で足り、安くて速い。
- ハッカソンのクレジットは AI Studio には使えず、Vertex AI 経由なら使える。
- Vertex AI は Cloud Run のサービスアカウントで呼べるので、API キーや鍵ファイルを作らずに済む（[技術設計書](design.md) 6章）。

**捨てた案**

- Pro 系：複雑な自由記述の読み取りは正確になるが、高くて遅い。今回の用途では差が出にくい。
- AI Studio 経由：クレジットが使えず、API キーの管理も要る。
- 他社 LLM：審査の「Google 技術」で評価されず、前面に出すと審査対象外になる。

## 6. 保存：計画は Firestore、入力データは JSON

**選んだ理由**

- 計画は保存しないと次の2つが両立しない。
  - UC-002：管理者が作った計画を、住民や家族が後から見る。
  - UC-004：管理者が条件を変えたら、見る側にも新しい計画が出る。
- Firestore は Firebase Hosting と同じプロジェクトで使え、待機中の料金がかからない。保存（FR-026）、比較（FR-027）、共有（FR-028）にもそのままつながる。
- 入力データ（架空の避難者、避難所、事前に取った距離行列）はデモ用の固定データなので、リポジトリの JSON にする。git で版を管理でき、テストでも同じファイルを使える。

**捨てた案**

- Cloud SQL：表どうしの関係を書けるが、インスタンスが動いている間ずっと課金され、$20 では 11/14 まで持たないおそれが高い。
- 入力も Firestore：画面から避難者や避難所を編集できるようになるが、作る量が増える。MVP では編集画面を作らない。
- 保存しない：一番速いが、UC-002 と UC-004 が両立しない。

**弱点と対策**

- Firestore の無料枠の量は未確認。デモの規模なら超えない見込みだが、実装前に公式の料金表で確かめる。

## 7. 移動時間：Routes API で事前に1回

**選んだ理由**

- 最適化には、地点どうしの移動時間の表（距離行列）が要る。実際の道路での時間を使うと、川や山を回り込む道を正しく扱える。
- デモ地域の距離行列を最初に1回だけ取って JSON に保存し、以降はそれを使う。有料の呼び出しは1回で済み、計算するたびに同じ値が使われるので結果も安定する。

**捨てた案**

- Routes API を毎回：通行止めなどの変化を反映できるが、計画を作り直すたびに課金され、$20 を使い切るおそれがある。
- 直線距離に係数：料金は 0 だが、川や山を越える区間で実際の時間と大きくずれる。

**弱点と対策**

- 事前に取った値なので、災害で道路が使えなくなっても反映されない。要件定義書 11 章のとおり、本システムは事前の計画作成と訓練に使うものとし、発災後の状況変化への対応は将来の拡張とする。

## 8. 実行基盤：Firebase Hosting と Cloud Run

**選んだ理由**

- 画面は Angular をビルドした静的ファイルなので、Firebase Hosting で配る。画面のためにサーバーを動かさずに済む。
- サーバーが要るのは、OR-Tools で計算するときと Gemini を呼ぶときだけなので、そこを Cloud Run（Python）に置く。Cloud Run は最小インスタンスを 0 にすると、使われていない間は課金されない。
- Firebase Hosting の rewrite で `/api/**` を Cloud Run に流す。画面と API が同じ URL になり、CORS の設定が要らない。審査員に渡す URL も1つで済む。Cloud Run を置く asia-northeast1 が rewrite に対応していることは、Firebase の公式ドキュメントで確認した。

**捨てた案**

- Firebase App Hosting：SSR のある構成向けで、デプロイのたびに Cloud Build が走る。今回は SSR を使わない。
- Cloud Run を2つ（画面用と API 用）：画面側は静的ファイルを配るだけなので、コンテナにする意味がない。
- Cloud Run を1つ：Angular と Python が1つのコンテナに同居し、画面だけを直したいときにも全体をデプロイし直すことになる。

**弱点と対策**

- Firebase Hosting はリクエストが 60 秒でタイムアウトする（公式ドキュメントに記載）。最適化の制限時間を 60 秒より十分短くする（[技術設計書](design.md) 4.3）。
- 最小インスタンスが 0 なので、しばらく使われていないと最初のリクエストで数秒待つ。審査員が開くたびに課金が続くよりもよいと判断した。

## 9. 型の共有：OpenAPI から生成

**選んだ理由**

- FastAPI が出す OpenAPI の仕様から、Angular 側の TypeScript の型を生成する。API を変えたとき、画面側の型が自動でそろい、片方だけ直してずれる事故が起きない。

**捨てた案**

- 手で書く：仕組みは要らないが、API を変えるたびに両側を直す必要がある。

**弱点と対策**

- 生成の手順が1つ増える。手順を README に書く。使う生成ツールは未決（[技術設計書](design.md) 8章）。

## 10. ログイン：作らない

**選んだ理由**

- オンライン会場の審査は、審査員が URL を開いて触ることになる。ログインがなければ、すぐに全機能を試せる。
- デモで扱うのはすべて架空の人物データで、守るべき実在の個人情報がない。

**捨てた案**

- Firebase Authentication：管理者だけが計画を変えられるようにでき、「安全性」で説明しやすい。しかし審査員用の入り方を別に用意する必要がある。
- 匿名ログイン：審査員の操作は増えないが、作る量に見合う効果が今回は小さい。

**弱点と対策**

- URL を知っていれば誰でも計画を作り直せる。デモ用の計画が壊されたときの扱いは未決（[技術設計書](design.md) 8章）。実際に運用するならログインが必要であることを、プロダクト説明ドキュメントに書く。
